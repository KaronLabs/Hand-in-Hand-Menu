# Hand in Hand QR 메뉴판 설계안

작성일: 2026-10-22 · 상태: 사용자 검토용 초안 · 제품 구현 및 외부 Site 생성 전

## 1. 목적과 성공 조건

손님이 테이블 QR을 스캔해 자신의 휴대폰에서 Hand in Hand 메뉴명·재료·가격을 읽는 사이트를 만듭니다. 로그인이나 앱 설치 없이 메뉴판이 열려야 합니다. 한국어 안내를 기본으로 하고, 원문 메뉴 이름을 함께 보존합니다.

사용자가 확정한 사항은 Hand in Hand 메뉴판, 제공한 기존 메뉴판 이미지 6장 활용, 손님 휴대폰 접속, 테이블 QR 제공입니다. 아이보리·브라운·앰버 색상, 텍스트형 메뉴, 분류 이동과 검색은 이번 검토안의 추천 사항입니다.

성공 조건은 원문에 근거한 메뉴 표시, 작은 화면에서의 가독성, 분류/검색 후 정확한 결과, 실제 배포 URL을 담은 QR, 비로그인 방문자의 접속입니다. 이번 단계는 설계·테스트 범위·구현 순서 확정이며 제품 코드와 실행 결과는 아직 없습니다.

## 2. 구현 방식 비교

| 방식 | 장점 | 한계 | 판단 |
| --- | --- | --- | --- |
| 정적 텍스트 메뉴 + 원본 이미지 보기 | 글자 크기 조절·분류·검색이 편하고, 원본과 대조 가능 | 최초 전사 검증과 가격 확인 필요 | 추천 |
| 원본 이미지 6장만 게시 | 원문을 그대로 제공하고 작업량이 적음 | 작은 화면에서 확대·좌우 이동 필요, 텍스트 검색 불편 | 보조 보기로 채택 |
| 관리자 화면 + 데이터베이스 | 직원이 가격·품절을 직접 수정 | 인증·권한·저장소·운영 테스트까지 추가 | 후속 확장 |

첫 버전은 정적 사이트로 구성합니다. 주문·결제·회원·예약·관리자 로그인·실시간 품절·개인정보 수집은 범위에 포함하지 않습니다. 고정 메뉴 URL 하나를 모든 테이블에서 사용하고 테이블 번호는 수집하지 않습니다.

### 3.1 가격 규칙

- 음식·칵테일 41개 행은 원본의 원화 정수 가격을 기록합니다. 예: 카쵸 에 페페 22,000원, 네그로니 22,000원, 리치맨스 모히토 28,000원.
- 위스키 29개 행의 Glass/Bottle은 `2,4`, `36` 같은 원문 문자열을 보존합니다. `2,4 → 24,000원`, `36 → 360,000원` 해석은 아직 사용자 확인을 받지 않았습니다.
- 위스키 단위는 데이터 파일의 확인 상태가 `verified`일 때만 원화로 변환합니다. 확인 전에는 수치 대신 `직원 문의`를 표시합니다. 이 정책은 가격이 없는 품목의 임의 추정을 막고 나머지 메뉴의 검증을 진행하기 위한 명시적 기본값입니다.
- Glenfiddich 21Y, Glenfarclas 105 CS, Glenfarclas 21Y의 양쪽 가격 칸은 비어 있습니다. 가격은 `null`, 상태는 `missing`, 화면은 `직원 문의`입니다. 0원이나 빈 원화 기호를 표시하지 않습니다.
- 확인된 위스키 단위가 만원이라면 문자열의 쉼표/소수점 1자리를 정확한 정수 계산으로 처리합니다. `2,4`는 24,000원, `36`은 360,000원, `130`은 1,300,000원입니다. 공백을 제거한 빈값은 `missing`입니다. 확인된 값은 양의 safe integer 원화여야 하며, 0·음수·문자 혼합·잘못된 구분자는 `invalid_price` 오류입니다. 단위 미확인은 변환을 수행하지 않고 `unverified`입니다.

### 3.2 이름·재료·출처 규칙

원문 이름과 재료는 별도 보존합니다. 고객용 한국어 이름 및 재료 번역은 출처와 일대일로 연결합니다. 원문 오탈자 수정은 `editorialNotes`에 전후를 기록하며 브랜드/제품을 근거 없이 바꾸지 않습니다. 도수·테이스팅 노트·인기 순위·추천 배지·알레르기 인증은 자료에 없으므로 생성하지 않습니다.

각 메뉴는 `id`, `categoryId`, `nameKo`, `nameOriginal`, `ingredientsKo`, `ingredientsOriginal`, `options`, `servingNote`, `price`, `sourceRefs`, `editorialNotes`를 가집니다. 재료와 editorialNotes는 문자열 배열이고, 옵션은 `{labelKo, labelOriginal}` 배열, servingNote는 문자열 또는 null입니다. ID는 `{categoryId}-{세 자리 원본 행 번호}`입니다. 예를 들어 카쵸 에 페페는 `food-001`, 네그로니는 `campari-005`입니다. 분류 ID는 `food`, `campari`, `italy`, `classic`, `modern`, `speyside`입니다. 동명이름도 원본 행 위치가 다르면 별도 ID를 유지합니다.

`price`는 `{kind:'single', single:Price}` 또는 `{kind:'whisky', glass:Price, bottle:Price}`입니다. `Price`는 `{amountKrw:number|null, status:'verified'|'unverified'|'missing', raw:string|null}`입니다. 미확인 상태의 `amountKrw`는 반드시 null입니다. `sourceRefs`는 `{fileName:string, pageId:string, rowIndex:number}` 배열이며 rowIndex는 1부터 시작합니다. `Category`는 `{id, titleKo, titleOriginal, sourceFile}`입니다. 루트 Menu는 `{categories, items, whiskyUnitStatus, sourceRowCount:70}`입니다. 고객용 중복 병합을 승인받아도 sourceRefs 총 70개의 원본 행을 잃어서는 안 됩니다.

## 4. 방문자 화면과 조작

1. 짧은 상단 영역에 `hand in hand`와 `메뉴`를 표시합니다. 과한 소개 화면 없이 메뉴가 첫 화면에 이어집니다.
2. 전체·푸드·캄파리 클래식·이탈리아 칵테일·클래식·모던·위스키 분류 버튼을 둡니다. 원본 영문 분류 이름도 각 섹션에 표시합니다.
3. 메뉴명·원문 이름·재료를 찾는 검색창을 둡니다. 분류와 검색어는 AND 조건이며, 공백만 있는 검색은 전체 결과입니다. 영문 대소문자와 Unicode 정규화 차이를 정규화합니다.
4. 메뉴 한 행에 이름, 재료, 가격을 표시합니다. 깔조네·피자 옵션과 아란치니 6개 표기를 유지합니다. 위스키는 잔/병 가격의 열 제목을 명확히 표시합니다.
5. 검색 결과가 없으면 `검색 결과가 없습니다`와 검색 초기화 버튼을 표시합니다. 검색 결과 개수를 보조기술이 읽을 수 있게 합니다.
6. 각 분류 아래의 `원본 메뉴판 보기`를 펼치면 관련 원본 이미지를 열 수 있습니다. 원본 보기는 JavaScript가 없어도 작동하는 기본 HTML 요소를 사용합니다.

모바일 320·390·430px에서는 단일 열, 768·1280px에서는 읽기 편한 최대 너비와 두 열까지 허용합니다. 아이보리 바탕과 브라운 텍스트, 앰버 강조를 사용합니다. 본문 16px 이상, 누르는 요소 44px 이상, 명확한 키보드 포커스, 본문 대비 4.5:1 이상을 목표로 검사합니다. 화면 확대와 가로모드를 막지 않습니다. 긴 제품명과 1,300,000원 가격 때문에 문서 전체에 가로 스크롤이 생겨서는 안 됩니다. 분류 영역의 의도적 가로 스크롤은 허용합니다.

## 5. 구조와 데이터 흐름

Node.js 24 이상의 빌드 도구가 확인된 메뉴 JSON을 검증하고 HTML을 사전 렌더링합니다. 배포물은 HTML·CSS·JavaScript와 로컬 이미지뿐입니다. 서버 API·DB·로그인은 필요하지 않습니다. 브라우저 JavaScript는 이미 표시된 메뉴의 분류/검색만 담당합니다.

`원본 6장 → 출처를 보존한 메뉴 데이터 → 검증·사전 렌더링 → Sites 고정 URL → QR → 손님 브라우저` 순서입니다. 구현 모듈은 데이터/가격 규칙, 메뉴 조회, HTML 렌더링, 브라우저 상호작용, 배포 URL 검증과 QR 생성으로 분리합니다.

HTML은 처음부터 모든 메뉴를 포함합니다. JavaScript가 실패하거나 꺼져도 가격과 메뉴를 읽을 수 있습니다. 검색 UI는 초기화가 성공했을 때만 사용 가능하게 해 고장 난 버튼을 노출하지 않습니다. 이미지 로딩 실패는 텍스트 메뉴를 가리지 않습니다. 메뉴 문자열은 HTML 텍스트로 안전하게 이스케이프합니다.

## 6. QR·접근권한·배포

사용자의 손님 접속 요청에 맞춰 공개 URL로 접근 가능한 Site가 필요합니다. Sites의 신규 기본값인 비공개와 구분해, 실제 손님용 배포 시 지원되는 공개 접근 설정을 확인합니다. 공개 설정이 허용되지 않으면 초대/로그인 링크를 QR로 대신 전달하지 않고 차단 사유를 보고합니다.

모든 테이블 QR은 같은 정식 메뉴 URL을 담습니다. 외부 단축 URL, 만료되는 미리보기 주소, 인증 우회 토큰, 사용자별 파라미터를 사용하지 않습니다. 플랫폼이 반환하는 정식 URL의 경로를 보존하며 루트 경로를 임의로 가정하지 않습니다. 이후 메뉴 수정은 동일 URL에 재배포해 이미 인쇄한 QR을 유지합니다. 슬러그·도메인을 바꾸면 QR 재발급 여부를 먼저 검토합니다.

등록 시 반환되는 `expected_url`은 초안 QR 생성에만 쓸 수 있습니다. 최종 QR은 배포 성공 응답의 실제 URL과 일치해야 합니다. PNG·SVG를 만들고 PNG를 별도 디코더로 다시 읽어 URL의 정확한 일치를 확인합니다. 흰 바탕, 검은 모듈, 최소 4모듈 여백, 오류 정정 M을 사용하며 로고를 덮지 않습니다. 실제 출력 QR은 30mm 이상을 권장하되, 출력본의 iPhone/Android 스캔은 별도 실물 검증 항목입니다.

메뉴 데이터 변경 후 전체 테스트·빌드를 통과한 커밋과 일치하는 배포물만 게시합니다. 가격 검토 결과·배포 버전·커밋 SHA·최종 URL·QR 디코딩 결과를 릴리스 기록에 남깁니다. 이전 배포 버전을 복구 수단으로 보존합니다. 메뉴 확인 정책상 `직원 문의`가 남아 있는 항목 수는 릴리스 기록에 공개합니다.

## 7. 테스트 범위와 합격 기준

| 경계 | 증명할 동작 | 방법/합격 기준 |
| --- | --- | --- |
| 원본→데이터 | 6분류 70원본 행의 누락·중복 덮어쓰기 방지, 원문 금액·옵션 일치 | 모든 행을 이미지와 사람이 대조. validator는 ID/출처 중복·누락/가격 상태의 구조 오류 검출 |
| 가격 | 미확인 단위 미변환, 빈값은 문의, 확인된 단위의 정수 변환 | 독립적으로 계산한 입력·기대값의 단위 테스트, core 100% line/branch/function |
| 조회 | 한글/영문/재료·대소문자·공백·분류 조합·초기화 | 실제 데이터 경로의 단위 테스트, core 100% |
| HTML | 사전 렌더링·잔/병 구분·옵션·빈 가격·이스케이프 | 생성 HTML을 파싱해 사용자에게 보이는 내용 검사, renderer 90% line/function 이상 |
| DOM | 분류 클릭·검색 입력·결과 개수·빈 결과·초기화·중복 초기화 | 실제 렌더러와 실제 클라이언트 모듈을 DOM에서 통합 검사, client 90% line/function 이상 |
| 화면 | 320/390/430/768/1280px, 긴 이름, 포커스, JavaScript 실패 시 가독성 | 지원되는 브라우저 QA. DOM 모사만으로 레이아웃 통과를 주장하지 않음 |
| QR | 다른 주소/임시주소 금지, QR 바이트가 최종 URL로 디코딩 | 생성 PNG를 독립 디코더로 읽고 최종 URL의 리터럴과 일치 |
| 공개 접근 | 시크릿/비로그인 세션에서 메뉴, 인증 리다이렉트 없음 | 지원되는 실제 비로그인 브라우저로 확인. 불가능하면 미검증으로 분리 |
| 게시물 무결성 | 커밋·메뉴·배포물·QR 대상 일치 | 릴리스 기록과 native Sites 성공 응답 대조 |

수치 커버리지는 지정한 모듈별 범위에만 적용합니다. CSS, 원본 이미지, JSON 데이터의 내용 정확성, 외부 라이브러리, Sites 내부는 코드 커버리지 분모에서 제외하고 각각 원본 대조·화면·경계 검증으로 확인합니다. 커버리지 100%를 전체 정확성이나 브라우저 호환성의 증명으로 표현하지 않습니다. 출처 기반 수작업 검증과 자동화 검증은 별개입니다.

실제 카메라·인쇄물·모든 휴대폰 모델·오프라인·부하·검색엔진 노출은 이번 자동 테스트 범위 밖입니다. 지원 환경에서 검증하지 못한 항목은 릴리스 결과에 미검증으로 기재합니다.

## 8. TDD 및 진행 단계

제품 코드를 쓰기 전에 한 동작의 실패 테스트를 만듭니다. 예상한 assertion 실패를 실제로 관찰한 뒤 최소 구현으로 통과시키고, 중복 정리는 통과 후 진행합니다. 모듈 파일이 없어서 import가 실패한 경우는 RED 증거가 아닙니다. 실행 가능한 최소 빈 모듈 경계를 만들고 소비자 결과에 대한 assertion 실패를 관찰합니다. 각 기능의 RED/GREEN/REFACTOR 증거와 전체 테스트 결과를 저장합니다.

현재 단계는 문서 초안 작성입니다. 다음 경계는 설계·계획 검토, 실행 방식 선택, 가격 단위 질문입니다. 실행 방식은 이 규모와 공통 데이터 의존성을 고려해 이 세션에서 직접 순차 구현하는 방식을 추천합니다. 구현은 승인된 문서와 선택된 실행 방식으로 시작합니다.

## 9. 검토·확인 목록

- [ ] 권장 구현 방식·화면 구성·범위에 대한 사용자 검토
- [ ] 위스키 가격 단위 확인: `2,4 = 24,000원`, `36 = 360,000원` 여부
- [ ] Balvenie 12Y 두 행이 같은 제품인지 확인; 확인 전 두 원본 행 유지
- [ ] 빈 가격 3종의 `직원 문의` 표기 수용 또는 실제 가격 제공
- [ ] 실행계획 검토와 직접 구현/하위 에이전트 방식 선택

확인 답변이 없을 때의 동작은 위에 명시돼 있습니다. 승인 전 제품 구현·의존성 설치·외부 Site 생성·배포는 수행하지 않습니다.
